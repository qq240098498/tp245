# 冷链温控与批次放行台

冷库与冷藏车的温控值班台：录冷库与探头、登批次、盯温度记录、算超限与断链、判放行还是拒收。

## 运行

```
npm install
npm start
```

默认端口 5245（`PORT` 可以覆盖），数据存在 `data/db.json`，页面在 `/`。

## 页面

- **概览**：冷库与运行/检修/停用数量、探头数量与已过校准期的探头数、批次总数与各状态条数、温度记录条数与人工记录数（另给被剔除出判定的记录条数）、放行与拒收条数、当前满足放行条件的批次数与被挡下的批次数、没有任何温度记录的批次数、最高与平均 MKT、按冷库一行给出探头与批次数；在办、可放行、被挡、无记录、MKT 都给**全部库 / 仅运行库 / 检修停用库**三套口径并可逐库看可放行与被挡数。
- **冷库与探头**：冷库台账（编码、名称、类型、位置、库位、状态、涉及批次）与探头台账（编号、所属冷库、位置、状态、校准有效期、记录条数、涉及批次数），都带增改删。冷库改成检修/停用、探头改成停用/送检时，保存后会给出**重算对照**。
- **批次**：批次清单（批次号、品名、规格、件数、所在冷库、冷库状态、入库时刻、状态、参与判定记录数/总记录数、最长超限、累计超限、MKT、断链数、放行情况），检修/停用冷库名下批次黄色单独标注；行内展开逐条温度记录（标明是否参与判定及原因）、超限段、断链缺口、放行判定五条、被剔除的探头明细、已过校准期探头与放行单（带当时存档结论与当前口径对照），并提供「放行」「拒收」入口。
- **温度记录**：记录清单（批次、探头、时刻、温度、来源、登记人、是否超限、是否参与判定），支持按批次、探头、来源、是否参与判定与时间筛选、单条新增与删除。非在用探头名下的历史记录仍列出可查。
- **放行台账**：放行与拒收记录（批次、决定、时刻、经办人、当时的 MKT、最长超限、累计超限、断链数与依据），每条带**当时完整判定快照**以及与当前口径的对照；历史结论不会因后来的状态变化被改写。

## 口径（页面上的说明与数字都要与本段一致）

1. **温度带**：默认 2 到 8 摄氏度（可在设置里改），低于下限或高于上限都算超限。
2. **超限段**：按时刻顺序逐条判，连续超限的时段算一段，**中间只要有记录回到范围内就断开**；每段的时长按该段相邻记录的实际时刻差累加。
3. **累计超限**：一个批次从入库到当前，所有超限段的时长之和；**跨月不重置**，按批次周期累计。
4. **断链**：相邻两条记录的时刻差超过 `chainGapMinutes`（默认 15 分钟）算一处断链，缺口时长按实际时刻差算。
5. **MKT（平均动力学温度）**：按动力学公式算，写成 `MKT = −Ea / (R × ln((Σ e^(−Ea/(R·T)) ) / n)) − 273.15`（活化能 Ea 取 83144 J/mol、气体常数 R 取 8.314，T 用开尔文，n 为参与计算的记录条数）；**不是把温度取平均**。
6. **放行判定五条**：至少有一条参与判定的温度记录（没有任何温度记录的批次不能放行）、单次连续超限不超过 `allowExcursionMinutes`（默认 30 分钟）、累计超限不超过 `allowTotalExcursionMinutes`（默认 120 分钟）、全程没有断链、**参与判定的探头都在校准有效期内**。五条同时满足才算满足放行条件；不满足时点「放行」会被服务端拒绝（错误码 `RELEASE_CHECK_FAILED`，`details.failed` 点名没过的条目）。
7. **同一探头同一时刻既有自动记录又有手工更正记录时，以手工记录为准**；**非在用（停用、送检）探头名下的记录不参与判定**——记录本身保留在台账里可查，批次详情与记录清单里标为「剔除」并写明因为哪台探头、什么状态、剔了几条；非在用探头不能登记新记录（历史记录不动）。
8. **检修与停用中的冷库**：其批次仍然照常记录与判定，但在批次清单与详情里黄色单独标注，概览与统计的「在办、可放行、被挡下、无记录、MKT」都分成全部库 / 仅运行库 / 检修停用库三套口径，可按冷库状态筛选批次。
9. **状态变更要有下文**：探头改成停用/送检（或恢复在用）后，保存响应里带 `impact`，把它名下记录涉及的每个批次的判定**改前/改后重算一遍**，页面弹出对照（结论是否翻转、参与记录数、MKT、超限、断链、翻转的判定条目）；冷库改成检修/停用或恢复运行后，`impact` 给出运行口径的在办/可放行/被挡前后变化。恢复在用、恢复运行后记录与批次自动回到参与判定的状态。
10. **历史结论不许悄悄改写**：每次放行/拒收都把当时的完整判定（含 MKT、超限、断链、剔除探头、失败条目）存成 `checkSnapshot`。之后探头或冷库状态变化只影响**当前**判定与统计，放行台账里的历史决定与存档数值保持原样，只额外显示「存档结论 vs 当前口径」的对照。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/health、/api/summary、/api/settings | 健康检查、概览、设置（PATCH 可改） |
| GET / POST | /api/rooms | 冷库清单（支持 status、type、keyword）/ 新增 |
| GET / PATCH / DELETE | /api/rooms/:id | 详情（含探头与批次）/ 修改（状态变化时响应带 `impact`：运行口径前后对照、名下批次）/ 删除 |
| GET / POST | /api/probes | 探头清单（支持 roomId、status）/ 新增 |
| PATCH / DELETE | /api/probes/:id | 修改（状态变化时响应带 `impact`：涉及批次判定逐条重算对照，含结论翻转、参与记录数、MKT、超限、断链）/ 删除 |
| GET / POST | /api/batches | 批次清单（支持 roomId、roomStatus、status、product）/ 新增 |
| GET / PATCH / DELETE | /api/batches/:id | 详情（含全部记录及参与判定标记、剔除记录、超限段、断链、放行单存档与当前对照）/ 修改 / 删除 |
| GET | /api/batches/:id/release-check | 这个批次当前的放行判定（五条；带 `excludedProbes` 被剔除探头明细、`totalRecordCount`/`excludedRecordCount`、冷库状态） |
| POST | /api/batches/:id/decision | 放行或者拒收，body `{decision, decider, decidedAt, basis, remark}`；放行单存 `checkSnapshot`。当前判定不满足时放行返回 409 `RELEASE_CHECK_FAILED` |
| GET / POST | /api/records | 温度记录（支持 batchId、probeId、source、from、to；每条带 `participates`、`excludedReason`）/ 新增（非在用探头返回 400） |
| DELETE | /api/records/:id | 删除一条记录 |
| GET | /api/releases | 放行台账（支持 batchId、decision）；每条带 `checkSnapshot`（当时判定存档）与 `current`（当前口径与是否已变化） |

`/api/summary` 在原有总数之外增加：`maintenanceRoomCount`、`stoppedRoomCount`、`stoppedProbeCount`、`excludedRecordCount`、`openByRoomStatus`，以及 `scope: { all, running, nonRunning }` 三套口径（在办、可放行、被挡下、无记录、最高/平均 MKT）；`rooms[]` 每行还带 `readyToRelease`、`blockedCount`。

出错的返回统一是 `{"error":{"code":"...","message":"...","details":{...}}}`，`details` 里会点名是哪个字段没过。
